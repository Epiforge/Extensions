An ordered query observes each element's keys itself rather than through a projection pairing the element with them, moves the element's position in place rather than splitting and rejoining the ordering three times, and looks for its new place outward from its old one before searching by halves; a key change allocates 87 B rather than 292 B and takes 0.26x the time in a view of a thousand elements and 0.14x in one of ten thousand, and building one takes 0.49x the time and allocates 0.57x as much.
A grouping or a lookup observes each element's key itself rather than through a projection pairing the element with it; an element changing group allocates 168 B rather than 592 B in a grouping and 896 B in a lookup, and takes 0.53x the time in a grouping of a thousand elements, 0.44x in a lookup and 0.27x in a grouping of ten thousand, and building a grouping takes 0.69x the time and allocates 0.81x as much.
A grouping or a lookup removes the element which actually left a group, where it removed the first element equal to it, so of two distinct elements which compare equal under one key, the one which stayed is no longer taken out in place of the one which changed group; the group finds the leaving element by reference, and from both ends at once where it occurs only once, so that one which joined its group lately or long ago is found almost at once, and an element changing group back and forth among 65,536 elements takes 0.032x the time.
Each element of a view holds less: 105 B less in a filtered view, 210 B less in a grouped one and 365 B less in a sorted one, since an observation no longer keeps a lock it needs only while it is built, an element occurring once in a filtered, projected, flattened or dictionary view no longer carries a list of its one position, a grouping or an ordering no longer keeps a projection beneath it, and an ordering by one key keeps that key in the element's entry rather than in an array of one; building a filtered view of a thousand elements allocates about 104 B less for each.
A dictionary built with ObserveToDictionary observes each element's key and value itself rather than through a projection pairing them; a change to an element's value takes 0.16x the time and allocates 560 B rather than 1,608 B, and building one takes 0.72x the time and allocates 0.74x as much.
Queries synchronized with a lock, a callback or a context, and not eventually, no longer take a lock around their queue of pending changes; one synchronized with a lock applies a change at once where it can take the lock without waiting and the change was not made within a handler of another query's announcement, and one synchronized with a context applies a change made on the context at once where none is pending; adding and removing an element costs 0.66x the time with a lock, 0.78x with a callback, 0.75x with a context and 0.61x on the context's own thread.
A query built over another reports that query's fault beside its own and drops it when it clears, where filtering, projecting, flattening, ordering, grouping, a lookup, converting to a dictionary, casting, filtering by type, distinct, skip, take, a slice, individual changes and the maximum of a projection lost it, as did a dictionary's filtering, filtering by type, conversion to a collection and concurrent form, so a fault arising beneath any of them no longer disappears from everything built on it.
A grouping, a lookup or an ordering, by its first key or a later one, whose key selector throws for an element leaves the element out and reports the fault until the selector stops throwing, as the readme says, where it threw a NullReferenceException out of the change which made the selector throw.
A dictionary whose key or value selector throws for an element leaves the element out and reports the fault until the selector stops throwing, where it mapped the key type's default, 0 for an int, to the value type's default.
First, FirstOrDefault, Last, LastOrDefault, ElementAt, ElementAtOrDefault, Single, SingleOrDefault, ElementAt given a function of the count, Sum and Average report a fault which appears or clears in the query they read even when its contents do not change, as Count and Any already did; so do a dictionary's Count, Sum and Average given a lambda and its Any given none, and a dictionary's ValueFor and ValueForOrDefault, which ignored its fault altogether.
A fault on a null element stops being reported once the element leaves a filtered, projected, flattened, grouped, sorted or dictionary view or a lookup, where it was reported for as long as the view lived.
A grouping, a lookup, an ordering, a dictionary, a filtered or projected view, and a dictionary's filtering, projection or conversion to a collection take up a change made on another thread to an element in the moment they begin observing it, where they could miss it and hold the element under its old key or value until it changed again; they now listen for an element's changes before reading it, and a dictionary's filtering, projection or conversion to a collection is built under its own lock, as the others are.
An observed expression whose evaluation two threads change at once is left announcing the later evaluation, where the thread announcing last could announce the earlier one and leave every view built on it holding a stale key or value until the next change.
An ordering by more than one key orders two elements which both lack a key at one level by the keys after it, where it treated them as equal whatever their later keys.
An ordering whose key selector the optimizer rewrites leaves its source's cache when its last observation is disposed, so observing it again yields a query which follows its source, where it yielded the disposed one.
