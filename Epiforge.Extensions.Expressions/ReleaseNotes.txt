A query built while what it is built over changes on another thread no longer misses that change. Each query now makes and announces its changes under a lock of its own, and a query being built reads what it is built over and subscribes to it while holding the locks of every query it reads through, taken in the order the queries were made. This is what left a filtered, projected, ordered, grouped, summed or keyed view built during a change without an element its source had, or with it out of place, and what threw InvalidOperationException out of filtering a dictionary being changed.
Observing a sequence which announces its changes now keeps a copy of it, changed only as its notifications arrive, so what the queries built over it read always matches what they have been told. When you ask a CollectionObserver to begin observing a sequence, make sure nothing changes it until the call returns; from then on it can change on any thread, provided a list announces its changes in the order it makes them. The copy costs a reference per element and, for a change far from the end of a long list, the time to move the rest of the copy. The observation now announces its Count changing and changed itself, around each change to its copy, whether or not the sequence does. A group of ObserveGroupBy or ObserveToLookup keeps no copy, reading its elements under its query's lock instead.
Observing a dictionary which announces its changes likewise keeps a copy, but brings each key a notification names into line with the dictionary itself, so notifications arriving in a different order from the changes they describe, as an ObservableConcurrentDictionary<TKey, TValue> changed by several threads allows, leave the observation agreeing with the dictionary. An add announced after a later change to the same key no longer throws ArgumentException into the thread which made it. Replacing a value with the same instance, or for a value type with an equal value, is no longer announced.
ObserveUsingSyncRootEventually, ObserveUsingSynchronizationCallbackEventually and ObserveUsingSynchronizationContextEventually now take what their source holds when it announces a reset, rather than when the reset reaches the thread they change on, so a change announced after the reset is no longer applied twice.
Asking to observe an expression containing a kind neither mechanism observes, such as a lambda passed as an argument, throws NotSupportedException naming its node type, such as Lambda, rather than the class representing it. Both readmes no longer list a lambda passed as an argument or an array built from bounds among what builds the graph instead, since neither is observed at all.
Disposing of a filtered or projected view of a sequence or a dictionary, or a collection built from a dictionary, while another thread changes what it is built over no longer throws InvalidOperationException, and no longer leaves the view watching an element the change added.
The sequences an ObserveSelectMany selector returns which announce their changes are now kept as copies changed only as their announcements arrive, so what a flattening shows always matches what it has announced, and a query built over it while one of them changes on another thread neither misses the change nor takes it twice. Such a sequence must not change while the flattening first reads it, which is when the flattening is built or when the selector first returns it.
A second operand of ObserveConcat which is not a query of this library is now observed like any other sequence, kept as a copy changed only as its announcements arrive, so what the concatenation shows always matches what it has announced. Such an operand must not change while the concatenation is built.
Changing a filtered or sorted view costs what it did, and changing a grouped view up to 3% more. Building a view over an observed sequence allocates the copy as well, 958 KB for a filtered view of a thousand elements where it was 950, and a live view holds 8 B more per element. Inserting and removing an element at the front of ten thousand observed elements costs 2.3 μs more for moving the copy, 1.6x what the list itself spends moving them. A query built over another now gives it a lock of its own, so a chain of seven queries built over an empty collection allocates 7,696 B where it allocated 7,200.
