# Benchmark comparison, 28 August 2026

Measured one day after the 27 August baseline, against the same hardware and the same runtime, with one change to the libraries: `ObservableCollectionSelectQuery` was rewritten to remove the two defects that baseline exposed.

This is not a release baseline. It measures unreleased code, and it exists to record what the fix actually bought and what it cost. The 27 August document remains the record of what shipped as Components 4.0.0, Collections 3.0.0 and Expressions 3.0.0.

It also adds four benchmarks that did not exist on 27 August: an indexed sweep of `where` and `select`, an enumeration of `orderBy` and `selectMany`, and a chained `where` into `select`. Two of those are here to measure a trade this change made, and two are here because writing the first two turned up defects worth recording before anyone tries to fix them.

## Reliability

Every row in this run has a standard deviation under five percent of its mean. One row should nonetheless not be compared across runs; see the last section.

## What changed

The rewrite touched one file. Three separate benchmarks moved, only one of which was the target.

| Measurement, 10,000 elements | 27 August | 28 August | |
|--- |---: |---: |---: |
| `ObserveSelect` value change | 4,997.0 ns | 429.35 ns | 11.6x |
| `ObserveAverage` value change | 5,406.7 ns | 645.4 ns | 8.4x |
| `ObserveOrderBy` key change | 11,961 ns | 7,181.5 ns | 1.67x |
| `ObserveSelect` enumeration | 16,326 ns / 40,096 B | 6,056.72 ns / 64 B | 2.7x / 627x |

The select enumeration figures for 27 August are from a measurement taken after that document was written, which is why they do not appear in it.

`ObserveAverage` and `ObserveOrderBy` were not modified. Both construct an `ObserveSelect` internally — average over its selector, order by over each of its key selectors — and both inherited the fix. The 27 August document predicted the average case from timing alone and recorded the prediction; this run confirms it against code that was never touched.

Everything else held. `ObserveWhere`, `ObserveAll`, `ObserveSelectMany`'s inner change, the raw source and the observable expression lifecycle are all within noise of 27 August, which is the evidence that this run is comparable to that one rather than merely different.

## What this run shows

**`ObserveSelect` no longer does work proportional to the collection.** The 27 August fit was 0.483 nanoseconds per element; it is now 0.026, eighteen times shallower and within a factor of two of `ObserveWhere`'s 0.015, which that document attributed to cache behavior rather than algorithm. Select now has the same shape as a constant-time path. Allocation is unchanged at a flat 400 bytes.

**The fix propagated to two queries that were not touched.** Average was predicted; order by was not. Its key-change slope halved, from 1.03 to 0.55 nanoseconds per element, because each of its key selectors is an `ObserveSelect`. What remains is order by's own repositioning work, which is expected of a sort.

**Enumeration composes with editing, as it already did for `where`.** `ChangeThenEnumerate` allocates 464 bytes at every size, exactly the 400 of a value change plus the 64 of an enumeration, and its time is within four percent of the sum of its parts. The copy-on-write snapshot only copies while an enumerator is actually open, so the edit-then-render cycle does not pay for one.

**Composing two queries costs about what the parts cost, and enumeration does not stack.** A chained enumeration is 88, 628 and 6,011 nanoseconds against the same select alone at 89, 626 and 6,057, with identical 64-byte allocation: only the outermost snapshot is materialized. A chained value change allocates a flat 488 bytes and grows with the same shape as its components.

**The indexer costs between one and two orders of magnitude more than the enumerator, and the gap widens with size.** Per element, walking a query by index against walking it by enumerator:

| | 100 | 1,000 | 10,000 |
|--- |---: |---: |---: |
| `ObserveWhere` | 9.9x | 25.0x | 78.9x |
| `ObserveSelect` | 15.1x | 22.8x | 67.4x |

Both queries store positions in a treap, so an indexed access is a descent rather than an offset, and at ten thousand elements that descent touches thirteen nodes scattered across a large heap. This is what `HasIndexerPenalty` exists to signal, and it is a larger number than the flag's presence in the code suggests. Note that the indexed path allocates nothing at all: this is purely a time cost.

**The rewrite made `ObserveSelect`'s indexer slower and its own benchmark says so.** The previous implementation held projections in a list and indexed in constant time; this one descends the treap. That is the cost of durable position handles, and it is why `HasIndexerPenalty` is now set on select, which keeps the library's own consumers on the enumerator. The consolation is that select's per-access cost lands at or below `where`'s at every size — 13.5, 14.3 and 40.8 nanoseconds against 13.6, 21.7 and 64.3 — so select now costs what the library already accepted for its other treap-backed query rather than something new. How much slower it is than the old list is not measured here; doing so would require reverting the file.

## Known issues visible in this run

**`ObserveOrderBy` copies its entire result on every enumeration.** 896, 8,096 and 80,096 bytes — eight bytes per element plus a fixed 96 — against a flat 64 for `where` and `select`. At ten thousand elements each enumeration allocates 80 kilobytes and promotes some of it. `GetEnumerator` is `results.ToList().AsReadOnly().GetEnumerator()`, which is the defect this document's predecessor found in select, unchanged.

**`ObserveSelectMany` is worse, and reaches the large object heap.** Its `GetEnumerator` materializes the inner enumerables, then filters, flattens, and copies again. At ten thousand teams that is 400 kilobytes and 342 microseconds per enumeration, roughly ten bytes per result. The backing arrays exceed the 85,000-byte threshold, so the allocation lands on the large object heap and forces full collections: the Gen2 count is 11.7 per thousand operations, where every other enumeration benchmark in this document is zero.

Neither is fixed here. Both want characterization tests written before the rewrite, which is how select was handled, and both belong to the same family — a query that derives its results on demand instead of maintaining them.

**`ObservableCollectionSelectQuery` still does not subtract a removed element's fault from `OperationFault`.** Faults clear when an element heals, but not when it is removed. This predates the rewrite and was deliberately preserved by it rather than changed during a performance change.

### Addendum, 28 August 2026

All three were fixed later the same day, on the same hardware.

Both enumerations now hold a shared snapshot which is discarded rather than patched when anything changes, so repeated reading is free and reading after a change costs what it did before. Neither needed the copy-on-write machinery the select query has, because neither ever mutates a snapshot in place.

| Enumeration, largest size | Before | After | |
|--- |---: |---: |---: |
| `ObserveSelectMany`, 10,000 teams | 341,787 ns / 400,229 B | 33,358 ns / 40 B | 10.2x / 10,006x |
| `ObserveOrderBy`, 10,000 elements | 20,032 ns / 80,096 B | 8,244 ns / 40 B | 2.4x / 2,002x |

The collection pressure is what actually went away. `ObserveSelectMany` reported 11.7 Gen2 collections per thousand operations in the run above, from backing arrays clearing the large object heap threshold; it now reports no Gen1 or Gen2 activity at all, and no Gen0 at a thousand teams and above. `ObserveOrderBy`'s 0.7 Gen1 collections per thousand operations are likewise gone.

The mutation rows held. `InnerAddAndRemove` moved from 140.5, 260.0 and 317.9 nanoseconds to 144.2, 263.8 and 318.1. `KeyChange` moved from 1,717, 2,658 and 7,182 to 1,762, 2,668 and 7,330. `SourceAddAndRemove` moved from 6,735, 8,002 and 15,797 to 7,245, 8,196 and 16,149; the smallest of those is a 7.6 percent shift with non-overlapping error bars, which is larger than the change can mechanically account for — one field assignment per notification — and smaller than the cross-run variance this document already records for allocation-heavy rows. It is noted rather than explained.

The fault defect was fixed separately: element faults are now removed when their element leaves, in both the select and where queries, which had disagreed about it.

## One row not to trust across runs

`ConstructAndDisposeAWhere` at ten thousand elements moved from 102,033 to 124,503 microseconds, twenty-two percent, while its standard deviation in both runs was under five percent. It allocated the same amount to within half a percent — 50,700 against 50,914 kilobytes — but incurred roughly thirty percent more collections in every generation. Nothing in this change touches `where`, and every other `where` row held within noise, so this reads as garbage collector scheduling rather than a code change. At fifty megabytes per operation this row is dominated by the collector's decisions and should be compared only within a run.
