# Benchmark baseline, 27 August 2026

Measured at the release of Epiforge.Extensions.Components 4.0.0, Epiforge.Extensions.Collections 3.0.0, and Epiforge.Extensions.Expressions 3.0.0.

This is the first recorded baseline. It exists so that the next release can quote a measured delta instead of a remembered one, and it records the libraries as they were actually shipped, defects included.

## Environment

```
BenchmarkDotNet v0.15.8, Windows 11 (10.0.26200.9168/25H2/2025Update/HudsonValley2)
Intel Core Ultra 9 275HX 2.70GHz, 1 CPU, 24 logical and 24 physical cores
.NET SDK 10.0.400
  [Host]     : .NET 10.0.11 (10.0.11, 10.0.1126.37416), X64 RyuJIT x86-64-v3
  DefaultJob : .NET 10.0.11 (10.0.11, 10.0.1126.37416), X64 RyuJIT x86-64-v3
```

Numbers from a different machine are not comparable to these. A future run intended for comparison should be taken on the same hardware, on an otherwise idle system, in Release.

## Reproducing

```
dotnet run --project Epiforge.Extensions.Benchmarking --configuration Release -- --filter *
```

Each mutation benchmark advances a cursor through its collection, so coverage sweeps every element regardless of how many iterations are run, and each mutation is either an involution or drawn from a stationary distribution, so no workload drifts over a long run.

## Reliability

Every row in this baseline has a standard deviation under six percent of its mean, and most are under two. No row was excluded as unreliable.

## What this baseline shows

**The raw collection is free and flat.** Adding and removing an element costs about 17 nanoseconds and 144 bytes no matter how many elements are present; a value change costs 9 nanoseconds. Everything below is what a query adds on top of that.

**A value change through `where` is essentially constant.** 91, 101 and 232 nanoseconds across a hundredfold increase in size, with allocation flat at 224 bytes. The growth that remains is consistent with cache behaviour rather than algorithmic cost — a ten thousand element graph has a working set of roughly fifty megabytes, and it stops fitting.

**Enumeration composes cleanly with editing.** `ChangeThenEnumerate` costs almost exactly `Enumerate` plus `ValueChangeKeepingMembership` at every size, and its 288 bytes is exactly the 64 of an enumeration plus the 224 of a value change. There is no hidden rebuild in the edit-then-render cycle.

**A structural change through `where` is dominated by building one observable expression.** Five to six microseconds and about six kilobytes per add-and-remove, against a control of 17 nanoseconds and 144 bytes. A single observable expression costs 2.8 to 4.7 microseconds and 4.3 to 4.6 kilobytes to create and dispose, which accounts for nearly all of it.

**Standing up a graph costs about five kilobytes per element.** 520 kilobytes at a hundred elements, 5.1 megabytes at a thousand, 50.7 megabytes at ten thousand — flat per element, and the single largest number in this document. Time per element runs from 3.8 to 10.2 microseconds. This is why an observable query is something to construct once and hold rather than build per frame or per request.

**`ObserveSelectMany` and `ObserveOrderBy` scale as designed.** An inner-collection change is 141 to 321 nanoseconds across the range, and an order-by key change allocates a constant 1.31 kilobytes at every size.

## Known issue visible in this baseline

`ObserveSelect` appears to do work proportional to the size of the collection when a single element changes. Its per-change cost fits `160ns + 0.48ns x n` closely: predicted 660 and 5160 nanoseconds at a thousand and ten thousand elements against measured 602 and 4997. By comparison the same fit against `ObserveWhere` gives a slope thirty-three times smaller, which is what a constant-time path with cache effects looks like.

`ObserveAverage` shows the same slope, 0.515 nanoseconds per element, which is consistent with it being built on top of `ObserveSelect` and inheriting the behaviour.

This is an inference from timing rather than from reading the implementation, and it is recorded here rather than fixed so that the fix has something to be measured against.

The inference was correct. `ObservableCollectionSelectQuery` stored a count of the positions each observable expression occupied rather than which ones, so every notification walked the entire projection list; it also rebuilt that list on every enumeration. Both were fixed the following day, and `ObserveAverage` improved without being touched, as predicted here. See `2026-08-28.md` for the measurement. The numbers above remain the behaviour that shipped.
